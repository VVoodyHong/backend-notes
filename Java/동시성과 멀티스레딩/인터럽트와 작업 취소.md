# 인터럽트와 작업 취소

## 핵심 정의
인터럽트(interrupt)는 스레드에게 실행을 중단하거나 대기에서 벗어나 달라고 알리는 협력적 신호다. `Thread.interrupt()`가 임의의 코드를 강제로 종료하는 것은 아니다. 작업은 인터럽트 상태를 확인하거나 인터럽트에 반응하는 블로킹 API를 호출해 종료 경로로 이동해야 한다.

비동기 결과의 취소(cancellation), 호출자의 대기 시간 초과(timeout), 실제 작업 종료는 서로 다른 사건이다. 이 구분을 놓치면 HTTP 응답은 이미 실패했는데 DB 쿼리·외부 호출·CPU 작업이 계속 자원을 사용하는 상황이 생긴다. API 설명은 Java SE 27 기준이다.

## 동작 원리 / 구조

| 동작 | 결과 상태·대기 | 실행 중 작업에 대한 효과 |
|---|---|---|
| `Thread.interrupt()` | 대상 스레드의 인터럽트 신호 | API별로 예외·대기 해제·플래그 설정; 강제 종료 아님 |
| `Future.get(timeout, unit)` | 시간 안에 결과가 없으면 호출자에게 TimeoutException | 자동 취소하지 않음 |
| 실행기에 제출한 `Future.cancel(true)` | 성공하면 취소 상태, get은 CancellationException | 일반 FutureTask는 실행 스레드에 인터럽트를 시도 |
| `CompletableFuture.cancel(true)` | 결과를 CancellationException으로 완료 | mayInterruptIfRunning 인자는 효과 없음 |
| `CompletableFuture.orTimeout(...)` | 같은 CompletableFuture를 시간 초과로 예외 완료할 수 있음 | 공급자 작업을 자동 중단하지 않음 |
| `ExecutorService.shutdownNow()` | 미시작 작업 반환, 새 작업 차단 | 실행 중 작업의 중단을 시도하며 종료를 기다리지는 않음 |

### 인터럽트를 처리하는 위치
`Thread.currentThread().isInterrupted()`는 상태를 읽고 유지한다. `Thread.interrupted()`는 **현재 스레드**의 상태를 읽은 뒤 지운다. `sleep`, `wait`, `join` 등에서 `InterruptedException`을 던질 때도 상태는 지워진다.

```java
// 호출자에게 InterruptedException을 전달할 수 없는 Runnable 경계
static void consume(java.util.concurrent.BlockingQueue<String> queue) {
    try {
        while (!Thread.currentThread().isInterrupted()) {
            String item = queue.take();
            process(item); // 장시간 계산이면 내부에도 취소 점검 지점 필요
        }
    } catch (InterruptedException interrupted) {
        Thread.currentThread().interrupt(); // 상위 실행 계층이 볼 수 있게 복원
    } finally {
        cleanup(); // 이 작업이 소유한 자원만 정리
    }
}
```

`process`·`cleanup`은 애플리케이션 작업을 나타낸다. 예외를 호출자에게 전파할 수 있는 메서드는 `throws InterruptedException`으로 전달하는 것도 적절하다. 복원한 뒤 같은 무한 대기 루프로 돌아가면 즉시 예외가 반복될 수 있으므로 이 예제는 정리 후 반환한다.

### 취소 신호가 자원에 미치는 영향
`FutureTask.cancel(false)`는 실행 중이면 항상 실패한다는 뜻이 아니다. OpenJDK jdk-25-ga 구현에서는 실행 중인 Callable이 아직 결과를 확정하지 않았다면 취소 상태로 바뀔 수 있으며, 실행 스레드에 인터럽트는 보내지 않는다. 그 후 본문이 값을 반환해도 Future 결과는 취소 상태로 남는다. false는 중단 신호를 보내지 않겠다는 선택이며, 결과를 계속 기다리겠다는 뜻이 아니다.

`InterruptibleChannel`의 블로킹 I/O에서는 인터럽트가 **채널을 닫고** `ClosedByInterruptException`을 발생시키며 인터럽트 상태는 유지된다(Java SE 25). 이미 인터럽트된 스레드가 이런 I/O를 호출해도 같다. 여러 작업이 채널을 공유한다면 한 작업의 취소가 다른 작업에도 영향을 줄 수 있다. 인터럽트 복원 후 같은 채널로 재시도·정리 I/O를 계속하는 코드는 이 부수 효과를 고려해야 한다.

## 실무 관점
- 인터럽트 예외를 로그만 남기고 무시하지 않는다. 계속 처리할 명시적 정책이 없다면 전파하거나 복원한 뒤 종료한다.
- `synchronized` 모니터 진입 대기는 인터럽트로 취소되지 않는다. 취소 가능한 락 대기가 필요하면 `lockInterruptibly()` 등 계약에 맞는 API를 사용한다.
- 소켓·JDBC·파일 I/O마다 인터럽트 반응과 자원 close 효과가 다르다. 호출 시간 제한, 드라이버 취소 API, 자원 소유권을 함께 설계한다. 취소했다는 이유만으로 원격 작업의 롤백이나 미실행을 단정하지 않는다.
- 전체 요청의 남은 시간 예산을 하위 호출에 전달한다. 각 단계마다 처음부터 긴 timeout을 새로 적용하면 전체 지연 상한을 지키기 어렵다.
- 작업을 취소한 뒤에도 실행 종료를 관찰하고 실행기를 정리한다. `Future.isDone()`이 true인 것은 취소 결과가 확정되었다는 뜻일 수 있으며 작업의 finally까지 끝났다는 보장은 아니다.

## 심화 Q&A

### Q. CompletableFuture를 취소했는데 왜 공급자 코드가 계속 실행되는가?
A. CompletableFuture는 결과를 완료하는 객체이며 일반 FutureTask처럼 실행 스레드를 취소하기 위해 소유하지 않는다. 취소는 결과와 종속 단계의 완료 상태를 바꾸지만 공급자 실행을 인터럽트하지 않는다. 실제 실행을 제어할 별도 Future, 취소 토큰 또는 자원별 취소 경로가 필요하다.

### Q. 시간 초과 후 재시도하면 어떤 중복이 발생할 수 있는가?
A. 첫 시도가 중단되지 않아 외부 시스템에서 성공한 뒤 재시도도 성공할 수 있다. 결과를 늦게 받은 것과 작업이 실행되지 않은 것은 다르다. 결제·주문 같은 부작용에는 멱등성 키·상태 조회·중복 방지 정책을 적용한다. 인터럽트나 Future 취소만으로 분산 작업의 원자성을 만들 수 없다.

### Q. CPU 계산은 언제 인터럽트를 확인해야 하는가?
A. 결과를 일관되게 버리거나 부분 진행을 복구할 수 있는 반복 경계에서 확인한다. 큰 계산 전체가 끝난 뒤만 확인하면 취소 응답이 늦고, 지나치게 세밀한 확인은 비용을 늘릴 수 있다. 체크 간격은 목표 취소 지연과 계산 비용으로 정한다.

### Q. shutdownNow 후 반환된 작업은 자동으로 취소된 Future인가?
A. 반환 목록은 실행을 시작하지 못한 Runnable이다. 반환된 FutureTask가 자동으로 취소 상태가 되리라고 일반화할 수 없다. 외부에서 그 Future를 기다리는 호출자가 있다면 명시적으로 취소·실패를 전달하는 종료 정책이 필요하다. 이미 실행 중이며 인터럽트를 무시하는 작업도 남을 수 있다.
