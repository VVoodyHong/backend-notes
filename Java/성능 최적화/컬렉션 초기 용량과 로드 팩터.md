# 컬렉션 초기 용량과 로드 팩터

## 핵심 정의
`ArrayList`, `HashMap`, `HashSet` 등 배열 기반 자바 컬렉션 프레임워크(Java Collections Framework) 구현체는 내부적으로 고정 크기 배열을 사용하다가 요소 수가 임계값을 넘으면 더 큰 배열로 재할당(resize)한다. 초기 용량(initial capacity)을 사용 목적에 맞게 미리 지정하면 이 재할당 횟수와 그 과정에서 발생하는 배열 복사(array copy)/재해싱(rehash) 비용을 줄일 수 있다.

로드 팩터(load factor)는 해시 테이블(hash table) 기반 컬렉션에서만 의미를 가지는 개념으로, 용량 대비 몇 퍼센트가 채워지면 리사이징을 트리거할지를 결정하는 값이다. `ArrayList`처럼 순차 배열 기반 구조에는 로드 팩터 개념 자체가 없다.

## 동작 원리 / 구조

### ArrayList의 용량 확장
```java
public ArrayList() {
    this.elementData = DEFAULTCAPACITY_EMPTY_ELEMENTDATA; // 빈 배열, 용량 0
}
```
기본 생성자는 실제로 용량 10짜리 배열을 즉시 만들지 않고, 빈 배열을 참조만 해두었다가 **첫 `add()` 호출 시점에** 용량 10으로 초기화한다(지연 초기화, lazy allocation). 이후 용량이 부족해지면 OpenJDK 25 구현은 다음 증가량을 선호하되, 요청한 최소 용량과 배열 최대 길이도 반영한다. API가 1.5배 성장을 보장하지는 않는다.

```java
int newCapacity = oldCapacity + (oldCapacity >> 1); // 약 1.5배
```

확장 시마다 `Arrays.copyOf()`로 전체 요소를 새 배열로 복사하므로, 요소 수가 많은 리스트에서 반복적으로 확장이 일어나면 누적 복사 비용(O(n) 복사가 여러 번)이 커진다.

```mermaid
flowchart LR
    A[new ArrayList] --> B[내부 배열 용량 0]
    B -->|첫 add| C[용량 10으로 할당]
    C -->|용량 초과| D["새 용량 = 기존 * 1.5"]
    D -->|Arrays.copyOf| E[전체 요소 복사]
```

### HashMap의 용량 확장과 로드 팩터
`HashMap`의 기본 초기 용량은 16, 기본 로드 팩터는 0.75다. 일반적인 put 경로에서는 새 매핑 삽입 후 `size > threshold`이면 리사이징이 발생해 배열 크기가 2배로 늘어나고 노드가 새 버킷으로 재배치된다. OpenJDK는 저장된 hash 비트로 분리하므로 모든 key.hashCode()를 다시 호출하지 않는다. 작은 테이블에서 충돌 체인이 길어져도 트리화 대신 확장할 수 있고, 최대 용량에서는 더 이상 두 배로 늘어나지 않는다. 자세한 내부 구조와 트리화(treeify) 조건은 [[HashMap 내부 구조]]에서 다룬다. 이 문서에서는 **용량/로드 팩터를 어떻게 사전에 설정할지**에 집중한다.

용량은 항상 2의 거듭제곱으로 정규화된다. 생성자에 임의의 수를 넣어도 `tableSizeFor()`가 그보다 크거나 같은 최소 2의 거듭제곱으로 올림한다.

```java
static final int tableSizeFor(int cap) {
    int n = -1 >>> Integer.numberOfLeadingZeros(cap - 1);
    return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
}
```

### 예상 요소 수 기반 초기 용량 계산
서로 다른 매핑 `n`개를 예상하면 Java 19+의 팩토리를 우선 사용한다. 기본 부하율을 반영하므로 원소 수와 내부 용량을 혼동하기 어렵다.

```java
Map<String, Object> map = HashMap.newHashMap(n);       // n개를 담기에 적절한 용량으로 생성
Set<String> set = HashSet.newHashSet(n);
Map<String, Object> lmap = LinkedHashMap.newLinkedHashMap(n);
```
`(int) (n / 0.75f) + 1`을 보편 공식으로 쓰면 경계에서 과도하게 할당할 수 있다. 예를 들어 `n=12`이면 17을 생성자에 전달해 내부 용량이 32가 되지만, 기본 부하율에서 12개는 용량 16에 들어간다. JDK 27에서 `HashMap.newHashMap(12)`와 비교해 이 차이를 확인했다. 구버전에서 수동 계산한다면 부하율을 반영한 올림, 숫자 범위와 최대 테이블 용량을 함께 처리한다. 예상 크기는 메모리 예산도 검증해야 한다.

`newHashMap(int numMappings)`은 인자를 "저장할 원소 개수"로 직접 받는다는 점이 기존 `new HashMap<>(initialCapacity)`와의 핵심 차이다. 기존 생성자의 `initialCapacity`는 원소 개수가 아니라 내부 테이블 크기를 의미해서, 개발자가 이 둘을 혼동해 용량을 잘못 지정하는 실수가 JDK 내부 코드에서도 여러 번 발견됐을 만큼 흔했다.

## 실무 관점
- **대량 데이터를 한 번에 적재할 때 필수적인 최적화**: 배치(batch) 처리, DB 조회 결과를 `Map`으로 변환, CSV 파싱 등 최종 크기를 미리 알 수 있는 상황에서 기본 용량(16 또는 10)으로 시작하면 데이터 크기의 로그에 비례하는 횟수로 리사이징이 누적된다. 반복 생성되는 컬렉션에서는 그 복사·할당 비용이 합산된다.
- **`ArrayList(int initialCapacity)` 활용**: `new ArrayList<>(expectedSize)`로 최종 크기를 미리 확보하면 `add()` 반복 중 배열 복사가 사라진다. `Collectors.toList()`처럼 크기를 예측할 수 없는 스트림 종단 연산은 이 최적화를 적용하기 어렵다.
- **로드 팩터를 낮추는 트레이드오프**: 같은 초기 테이블 용량에서 로드 팩터를 0.5처럼 낮추면 더 적은 원소 수에서 확장 임계값에 도달한다. 충분히 분산된 해시에서는 버킷당 평균 충돌을 줄일 수 있지만, 메모리·캐시 비용도 늘 수 있으므로 조회 성능 향상을 보장하지는 않는다. 조회가 매우 빈번하고 메모리 여유가 있는 캐시성 `Map`이라면 고려할 만하지만, 대부분의 경우 기본값 0.75가 시간/공간의 합리적 절충점이다.
- **과도한 사전 할당의 역효과**: 실제 사용량보다 훨씬 큰 초기 용량을 지정하면 `ArrayList`는 즉시 배열을 할당하고 `HashMap`은 첫 삽입 시 그 크기의 버킷 배열을 할당해 낭비할 수 있으며, 순회 성능(`iteration`)도 빈 버킷이 많아질수록 오히려 저하된다(`HashMap`의 순회 비용은 용량에도 비례한다). 정확한 예측이 어렵다면 대략적인 상한으로 추정하되 지나치게 여유를 두지 않는다.
- **`HashSet`은 내부적으로 `HashMap`을 감싼 구현**이므로 동일한 용량/로드 팩터 전략이 그대로 적용된다.
- **불변 컬렉션과의 구분**: `List.of()`, `Map.of()` 등 불변 팩토리는 크기가 고정되어 리사이징 개념 자체가 없으며, 가변 컬렉션보다 메모리 오버헤드가 작게 설계되어 있다. 크기 변경이 없는 상수성 데이터는 가변 컬렉션 대신 불변 팩토리를 우선 고려한다.

## 심화 Q&A

### Q. `ArrayList`의 기본 생성자를 쓰면 왜 즉시 용량 10을 할당하지 않고 지연시키는가?
빈 리스트로 생성됐다가 실제로는 한 번도 요소가 추가되지 않고 버려지는 경우(예: 조건부로만 채워지는 지역 변수)가 실무에서 드물지 않기 때문이다. 즉시 할당하면 이런 경우에도 불필요한 배열 할당이 발생한다. 지연 초기화를 통해 실제로 `add()`가 호출되는 시점까지 할당을 미뤄, 사용되지 않는 리스트에 대한 메모리 낭비를 없앤다.

### Q. 초기 용량을 정확히 예상 크기로 맞춰도 리사이징이 발생할 수 있는가?
`HashMap`은 그렇다. 예상 요소 수를 `n`이라 할 때 `new HashMap<>(n)`처럼 용량 자체를 `n`으로 넘기면, 실제 트리거 조건은 `size > capacity * 0.75`이므로 `n`개를 다 채우기 전에 이미 리사이징 임계값을 넘어설 수 있다. 로드 팩터를 반영한 용량이나 `HashMap.newHashMap(n)`을 사용하면 요소 수 임계값 때문에 발생하는 확장을 줄일 수 있다. 이 팩토리도 작은 테이블에서 과도한 해시 충돌 때문에 발생하는 확장까지 금지하지는 않는다.

### Q. `ArrayList`의 성장 비율이 2배가 아니라 1.5배인 이유는?
2배 확장은 메모리 낭비 측면에서 불리하다. 특히 큰 리스트일수록 확장 시 순간적으로 필요한 메모리가(기존 배열 + 새 배열이 공존하는 복사 구간 동안) 기존 크기의 3배에 달할 수 있는데, 2배 성장은 이 순간 최대치를 더 키운다. 1.5배는 확장 빈도와 낭비되는 여유 공간 사이의 절충으로 선택된 값이며, `ArrayDeque` 등 다른 컬렉션은 다른 성장 비율을 쓰기도 한다.

### Q. 초기 용량 지정이 `LinkedList`에는 왜 의미가 없는가?
`LinkedList`는 배열이 아니라 이중 연결 리스트(doubly linked list) 노드로 요소를 저장하므로 애초에 "용량"이라는 개념 자체가 없다. 각 `add()`는 새 노드를 힙에 개별 할당하는 것이지, 배열을 리사이징하는 것이 아니다. 따라서 초기 용량/로드 팩터 최적화는 배열 기반 구조인 `ArrayList`, `HashMap`, `HashSet`, `ArrayDeque` 등에만 적용되는 개념이다.

### Q. `Map`을 캐시로 쓸 때 초기 용량을 넉넉하게 잡는 것이 항상 유리한가?
그렇지 않다. 캐시의 상한과 함께 퇴출(eviction) 시점도 확인해야 한다. Java SE 25의 `LinkedHashMap.removeEldestEntry()`는 새 항목 삽입 후 호출된다. OpenJDK 25의 일반 `put` 경로는 임계값 초과에 따른 확장을 먼저 수행하고 그 뒤 오래된 항목을 퇴출한다. 따라서 최대 12개를 유지하는 캐시도 용량 16·부하율 0.75에서 13번째 서로 다른 키를 넣으면, 최종 크기는 다시 12개가 되지만 테이블은 이미 32로 늘어날 수 있다. 이 확장까지 피하려면 정상 상태의 상한뿐 아니라 퇴출 전의 일시적인 크기와 부하율도 계산에 넣는다.

반대로 상한보다 훨씬 크게 초기 용량을 잡으면 캐시가 거의 비어 있는 상태에서도 큰 버킷 배열을 유지하게 되어 인스턴스당 메모리 오버헤드가 커지고, 다수의 캐시 인스턴스를 운영하는 서비스에서는 이 낭비가 누적되어 전체 힙 사용량에 영향을 줄 수 있다.

### Q. 리사이징 비용은 GC에 어떤 영향을 미치는가?
`ArrayList`나 `HashMap`의 리사이징은 기존 배열을 그대로 둔 채 새 배열을 할당하고 데이터를 복사한 뒤 기존 배열 참조를 버리는 방식이므로, 리사이징이 반복될수록 짧은 생명주기의 큰 배열들이 계속 생성되어 할당·GC 압박을 준다. 큰 배열은 G1의 humongous 객체처럼 Young을 거치지 않는 경로로 할당될 수도 있다. 대량의 컬렉션을 반복적으로 채우는 배치 작업에서 초기 용량을 지정하지 않으면 이 과정에서 발생하는 임시 배열들이 Minor GC 빈도를 늘리는 원인이 될 수 있으며, [[GC 튜닝]]에서 다루는 할당률(allocation rate) 문제와 직접 연결된다.
