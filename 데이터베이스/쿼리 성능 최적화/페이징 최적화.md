# 페이징 최적화

## 핵심 정의

페이징(pagination)은 대량 결과를 일정 개수씩 나눠 조회하는 방식이다. 가장 흔한 방식인 오프셋 기반 페이징(offset pagination, `LIMIT n OFFSET m`)은 구현이 단순하지만 뒷페이지로 갈수록 DB가 앞의 `m`개 행을 스캔 후 버려야 해서 페이지 번호가 커질수록 선형적으로 느려진다. 이를 해결하는 대안이 키셋 페이징(keyset pagination, seek method, cursor 기반 페이징)으로, 마지막으로 조회한 행의 키 값을 기준으로 "그다음 값부터" 바로 찾아가는 방식이다.

이 노트는 SQL의 스캔 비용과 인덱스·지연 조인 최적화에 초점을 둔다. API 응답과 클라이언트의 목록 탐색 방식은 [[페이지네이션 전략]]에서 다룬다.

## 동작 원리 / 구조

### 오프셋 페이징의 비용 구조

```sql
SELECT id, title, created_at
FROM articles
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100000;
```

이 쿼리는 인덱스를 타더라도 `OFFSET` 이전 100,000개 행을 인덱스에서 순서대로 읽고 버린 뒤에야 20개를 반환한다. 페이지가 깊어질수록(offset 증가) 스캔 비용이 그대로 증가하는 O(offset + limit) 패턴이다.

```mermaid

    A[정렬된 인덱스 시작] -->|100000건 스캔+폐기| B[원하는 구간 도달]
    B -->|20건 반환| C[결과]
```

### 키셋 페이징(Seek Method)

정렬 기준 컬럼 + 고유 식별자(tie-breaker)를 복합 인덱스로 만들고, `WHERE`절에서 "마지막으로 본 값보다 작은/큰" 조건으로 시작 지점을 지정한다.

```sql
CREATE INDEX idx_articles_keyset ON articles (created_at DESC, id DESC);

-- 첫 페이지
SELECT id, title, created_at FROM articles
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- 다음 페이지 (마지막 행: created_at='2026-01-15 10:00:00', id=12345)
SELECT id, title, created_at FROM articles
WHERE (created_at, id) < ('2026-01-15 10:00:00', 12345)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

정렬 컬럼이 유니크하지 않으면(`created_at` 중복 가능) 반드시 PK 같은 유니크 컬럼을 튜플 비교(row value syntax)에 포함해 동률(tie) 문제를 없애야 한다. 정렬 방향은 정방향 또는 전체 역방향 스캔과 맞아야 한다. 혼합 ASC/DESC는 각 방향을 고려한다. MySQL 8.4는 튜플 부등식이 복합 인덱스 전체 범위를 잘 활용하지 못하는 경우가 있으므로 `created_at < :t OR (created_at = :t AND id < :id)`로 풀어 쓴 조건과 실행 계획을 비교한다.

키셋 페이징은 적절한 인덱스와 필터 조건에서 대략 O(log N + limit)의 탐색·스캔으로 페이지 깊이에 따른 앞부분 폐기를 피한다. 인덱스에 없는 필터나 낮은 선택도·MVCC 검사 때문에 limit보다 많은 후보를 읽을 수 있다.

### 커버링 인덱스 + 지연 조인(Deferred Join) 패턴

임의 페이지 번호 이동(page=N)처럼 OFFSET을 완전히 제거할 수 없는 경우, 커버링 인덱스로 PK만 먼저 빠르게 추려낸 뒤 본문 컬럼을 조인해서 가져오면 랜덤 I/O를 줄일 수 있다.

```sql
SELECT a.* FROM articles a
JOIN (
  SELECT id FROM articles
  ORDER BY created_at DESC, id DESC
  LIMIT 20 OFFSET 100000   -- id만 다루므로 커버링 인덱스로 가볍게 스캔
) t ON a.id = t.id
ORDER BY a.created_at DESC, a.id DESC;
```

내부 서브쿼리가 인덱스만으로(커버링) 처리되므로, 매 행마다 전체 컬럼을 읽어 버리는 것보다 스캔 비용이 줄어든다. 다만 OFFSET 자체의 O(offset) 특성은 여전히 남는다 — 근본 해법은 키셋 페이징이다.

### COUNT(*) 총 페이지 수 문제

"전체 N페이지" UI를 위한 `COUNT(*)`는 대형 테이블에서 그 자체로 풀스캔에 가까운 비용이 든다(InnoDB는 트랜잭션별 가시 행이 달라 카운트를 캐시하지 않음). 정확한 총 개수 대신 "다음 페이지 있음/없음"만 판단하거나(limit+1개 조회), 근사치 카운트, 무한 스크롤 UX로 대체하는 것이 실무적 해법이다.

### NULL을 포함하는 키셋 커서

PostgreSQL 18에서 DESC의 기본값은 `NULLS FIRST`이며, MySQL 8.4는 DESC에서 NULL을 마지막에 놓는다. 같은 `ORDER BY created_at DESC`라도 NULL 행의 위치가 다르다. 아래처럼 PostgreSQL에서 NULL을 마지막으로 고정했다면 커서 조건도 그 순서를 따라야 한다. `id`는 NOT NULL인 고유 키라고 가정한다.

```sql
-- PostgreSQL 18: 비NULL 커서 뒤에서 NULL 구간까지 이어 읽기
SELECT id, title, created_at
FROM articles
WHERE created_at < :cursor_time
   OR (created_at = :cursor_time AND id < :cursor_id)
   OR created_at IS NULL
ORDER BY created_at DESC NULLS LAST, id DESC
LIMIT 20;

-- 커서가 NULL 구간에 진입한 뒤
SELECT id, title, created_at
FROM articles
WHERE created_at IS NULL AND id < :cursor_id
ORDER BY created_at DESC NULLS LAST, id DESC
LIMIT 20;
```

첫 페이지도 같은 정렬을 사용하고, 커서는 시각의 NULL 여부와 ID를 함께 보존한다. 일반 부등식만으로는 NULL 구간을 이어 읽을 수 없다. 임의의 기본 시각으로 COALESCE하면 실제 데이터와 충돌하거나 표현식 인덱스가 필요해질 수 있으므로 데이터 도메인과 계획을 확인한다. PostgreSQL 인덱스도 `(created_at DESC NULLS LAST, id DESC)`처럼 정렬을 맞출 수 있지만, 위 OR 조건에서 읽는 후보 수는 실행 계획으로 확인한다.

### 변경되지 않는 ID도 일관된 스냅샷을 뜻하지 않는다

키셋은 정렬 위치를 이어 주지만 페이지 사이의 가시성까지 고정하지 않는다. PostgreSQL 18의 READ COMMITTED에서 A가 시퀀스 기반 ID 1을 INSERT한 채 미커밋이고 B가 ID 2를 먼저 커밋하면, `WHERE id > 0 ORDER BY id LIMIT 1`은 2를 반환한다. 이후 A가 커밋해도 다음 조건 `id > 2`에는 1이 들어오지 않는다. ID가 불변·고유해도 발생하며, 시작 시 `MAX(id)=2`를 상한으로 저장하는 것만으로도 해결되지 않는다.

일반 목록은 이런 동시 변경을 허용할 수 있지만 전량 내보내기·백필은 대상 집합을 먼저 정한다. PostgreSQL REPEATABLE READ의 한 트랜잭션에서 같은 스냅샷을 유지하면 시작 시 가시 집합을 일관되게 읽을 수 있으나, 그 뒤 커밋된 행은 그 집합에 포함되지 않으며 긴 트랜잭션은 [[MVCC]]·VACUUM 비용을 늘린다. 계속 유입되는 작업을 빠짐없이 처리해야 한다면 ID 커서만으로 완료를 판단하지 말고 [[트랜잭셔널 아웃박스]]의 미처리 상태나 변경 로그 기반 진행 위치처럼 복구 가능한 기준을 사용한다.

## 실무 관점

- **언제 오프셋을 써도 되는가**: 페이지 이동 폭이 얕고(초반 몇 페이지) 전체 데이터 규모가 작거나, 임의 페이지 번호 점프(관리자 페이지네이션 UI)가 꼭 필요한 경우엔 오프셋 방식이 구현 단순성 면에서 여전히 실용적이다.
- **언제 키셋으로 전환해야 하는가**: 무한 스크롤, API 커서 기반 목록, 대량 데이터의 뒷페이지 접근이 잦은 서비스(피드, 로그 조회)는 키셋 페이징이 필수에 가깝다.
- **트레이드오프**: 키셋 페이징은 "임의 페이지로 바로 점프"가 불가능하고(이전/다음만 자연스러움), 정렬 기준이 바뀌면 커서 값 구성도 바뀌어야 해서 API 설계가 오프셋보다 복잡하다. 커서 값을 클라이언트에 노출할 때는 불투명 토큰으로 표현할 수 있다. base64는 표현 인코딩일 뿐 비밀성·변조 방지를 제공하지 않는다. 권한과 필터 조건을 서버에서 검증하고 필요하면 서명·암호화 또는 서버 측 커서 상태를 사용한다.
- **흔한 실수**: 정렬 컬럼에 유니크 tie-breaker를 넣지 않아 동일 시각 데이터가 누락/중복되는 버그, 인덱스 컬럼 순서가 `ORDER BY`와 불일치해 filesort가 발생하는 경우, `created_at`이 NULL 허용 컬럼일 때 비교 연산자가 NULL 행을 자동으로 걸러내 버리는 문제.
- **관련 튜닝 포인트**: 정렬+필터 조건을 모두 포함하는 복합 인덱스 설계(`(status, created_at, id)` 형태), `EXPLAIN`으로 filesort/Using temporary 발생 여부 확인, 대시보드성 페이지 수 표시는 근사치나 캐시된 카운트로 대체.

## 심화 Q&A

### Q. 키셋 페이징에서 정렬 컬럼이 중복 값을 가질 때 어떤 문제가 생기고 어떻게 해결하는가?
`created_at`처럼 동일 값이 여러 행에 걸쳐 있으면 단일 컬럼 비교(`WHERE created_at < ?`)만으로는 경계에 걸친 행이 누락되거나 중복 반환될 수 있다. 해결책은 PK 같은 유니크 컬럼을 tie-breaker로 추가해 튜플 비교(`WHERE (created_at, id) < (?, ?)`)를 사용하고, 인덱스도 `(created_at, id)` 순서로 구성하는 것이다.

### Q. 임의 페이지 번호로 점프해야 하는 요구사항과 키셋 페이징은 근본적으로 상충하는가?
그렇다. 키셋 페이징은 "직전 커서 위치"를 알아야 다음 구간을 찾을 수 있는 구조라 페이지 5에서 바로 페이지 50으로 점프하는 연산이 자연스럽지 않다. 이런 요구가 있다면 (1) 오프셋 방식을 유지하되 지연 조인으로 비용을 줄이거나, (2) 검색 엔진/캐시 계층에 미리 정렬된 ID 목록을 적재해 점프를 지원하는 등 아키텍처 차원의 타협이 필요하다.

### Q. LIMIT/OFFSET과 키셋 방식의 실행 계획 차이를 어떻게 확인하는가?
`EXPLAIN ANALYZE`에서 Limit 아래의 실제 읽은 후보 행 수·loops·정렬을 비교한다. 옵티마이저의 `rows`는 노드별 조건 통과 추정치이므로 OFFSET+LIMIT 또는 LIMIT과 반드시 같지 않다. 키셋 조건이 Index Cond/range에 포함되는지와 추가 필터로 버린 행도 확인한다.

### Q. 정렬 기준 컬럼이 자주 갱신되는 값(예: 좋아요 수, 최근 활동 시각)이면 키셋 페이징을 어떻게 적용하는가?
정렬 기준 값이 조회 도중 바뀌면 커서 기준 위치도 흔들려 행이 누락되거나 중복 노출될 수 있다. 완벽한 해결은 어렵지만, (1) 정렬 값에 스냅샷 시점을 고정하거나, (2) 정렬 기준 자체를 안정적인 생성 시각 등으로 바꾸거나, (3) 사용자 경험상 약간의 중복/누락을 허용하는 방향으로 타협하는 것이 일반적이다.

### Q. COUNT(*)를 없애고 "다음 페이지 존재 여부"만 알고 싶을 때 어떻게 구현하는가?
요청한 limit보다 1개 더 많이 조회(`LIMIT n+1`)해서, 반환된 행 수가 n+1이면 다음 페이지가 있다고 판단하고 마지막 1개는 응답에서 제외한다. 이 방식은 별도 COUNT 쿼리 없이 페이지네이션 UI에 필요한 최소 정보만 저비용으로 얻을 수 있다.

### Q. 커버링 인덱스와 키셋 페이징을 함께 쓰면 어떤 상승효과가 있는가?
키셋 페이징은 WHERE 조건으로 시작 지점을 바로 찾아가 스캔 범위 자체를 limit 수준으로 줄이고, 커버링 인덱스는 그 범위 내에서 테이블(힙/클러스터형 인덱스) 접근 없이 인덱스만으로 응답을 완성한다. 두 기법을 결합하면 적절한 인덱스·필터와 가시성 상태에서 스캔량과 테이블 접근을 함께 줄일 수 있어, 대규모 피드/로그성 API에서 사실상 표준 조합으로 쓰인다.
