# 분산 ID 생성

## 핵심 정의

분산 ID 생성(distributed ID generation)은 여러 서버/인스턴스가 동시에 데이터를 생성해도 서로 충돌하지 않는 고유 식별자(unique identifier)를 중앙 조정 없이(또는 최소한의 조정으로) 만들어내는 문제를 다룬다. 샤드별로 같은 범위의 auto-increment를 쓰면 충돌하므로 범위를 나누거나 샤드 ID를 결합해야 한다. 중앙 시퀀스는 처리량·가용성 의존성을 만들 수 있어, 이를 해결하기 위한 여러 방식이 발전해 왔다.

## 동작 원리 / 구조

### 대표 방식 비교

| 방식 | 정렬 가능성 | 크기 | 충돌 가능성 | 비고 |
|---|---|---|---|---|
| DB auto-increment | 할당 순차, gap·커밋 순서 역전 가능 | 자료형에 따라 다름 | 유니크 제약·범위 관리 필요 | 샤딩 환경에서 확장 어려움 |
| UUID v4(랜덤) | 없음 | 128bit | 이론상 존재(무시 가능) | 인덱스 지역성 나쁨 |
| UUID v7(시간 기반) | 대략적 시간순 | 128bit | 이론상 존재(무시 가능) | RFC 9562(2024)로 표준화, v4와 호환되는 컬럼 타입 사용 가능 |
| Snowflake(트위터) | 대략적 시간순 | 64bit(정수) | 노드ID·시계·시퀀스 관리 오류 시 발생 | 타임스탬프+노드ID+시퀀스 조합 |
| DB 구간 할당(segment) | 구간 내 순차, 전역 순서 미보장 | 임의 | 구간을 원자적으로 중복 없이 할당해야 함 | 여러 노드가 구간 단위로 번호를 미리 발급받음 |

### Snowflake 구조

Twitter의 `snowflake-2010` 소스는 노드 부분을 데이터센터 5비트·워커 5비트로 나눈다. 이를 합쳐 표현하면 다음과 같다.

```
| 1bit 부호(항상 0) | 41bit 타임스탬프(ms) | 10bit 노드/워커 ID | 12bit 시퀀스 |
```

- 41비트 타임스탬프는 커스텀 에폭(epoch) 기준으로 약 69년 표현 가능.
- 10비트 노드 ID로 최대 1024개 노드를 구분(예: 데이터센터 ID 5bit + 워커 ID 5bit로 세분화하기도 함).
- 12비트 시퀀스는 같은 밀리초 내에서 한 노드가 발급할 수 있는 최대 4096개의 ID를 순차 증가시켜 구분.

```java
// 비트 조립만 보여주는 예시: ts는 epoch 경과 ms, nodeId는 0~1023,
// sequence는 0~4095이며 이 세 값의 유일성은 생성기 상태 머신이 보장해야 한다.
long id = (ts << 22) | (nodeId << 12) | sequence;
```

완전한 생성기는 동기화된 임계 구역에서 마지막 시각과 시퀀스를 갱신하고, 같은 밀리초에 시퀀스가 넘치면 다음 밀리초까지 기다리며, 시각이 바뀌면 시퀀스를 초기화한다. 비트 마스킹만 하고 넘침을 기다리지 않으면 중복 ID를 만든다.

노드 ID는 코디네이터의 임대나 정적 할당으로 관리할 수 있다. StatefulSet 서수는 해당 StatefulSet 안에서만 고유하므로 클러스터·리전·다른 StatefulSet 간 네임스페이스를 함께 배정한다. 임대 만료 후 이전 프로세스가 계속 발급하거나 재시작 후 같은 밀리초·시퀀스를 재사용하는 상황도 방어해야 한다. 시계가 역행(clock rollback)하면 같은 타임스탬프+시퀀스 조합이 재사용되어 중복이 발생할 수 있으므로, 대부분의 구현체는 시계 역행을 감지하면 예외를 던지거나 짧게 대기한다.

### UUID v7 구조 (RFC 9562, 2024년 표준화)

```
48bit Unix 타임스탬프(ms) | 4bit 버전(0111) | 12bit rand_a | 2bit variant(10) | 62bit rand_b
```

상위 48비트로 대략적인 시간순 정렬이 가능해 v4보다 인덱스 지역성을 개선할 수 있다. 나머지 74비트는 랜덤으로 채우거나, 선택적인 sub-millisecond 시간(최대 12비트)·카운터·랜덤 조합을 쓸 수 있다. 같은 밀리초 안의 단조성은 구현 선택이며, 노드 간 시계 차이 때문에 전역 실제 생성 순서는 보장되지 않는다. UUID 저장 타입·문자열 형태는 v4와 같지만 v4만 허용하던 검증기·버전 가정은 바꿔야 한다.

### DB 구간 할당 방식

여러 애플리케이션 노드가 매번 DB에 접근하지 않고, 한 번에 "1000~2000번 구간"처럼 번호 구간을 미리 할당받아 메모리에서 소진하는 방식이다. Meituan Leaf의 segment 모드가 이 방식의 사례다. DB 부하를 줄이지만 노드별 구간이 병렬로 소진되므로 전역 발급 순서나 연속 번호를 보장하지 않는다. 예를 들어 노드 A의 1001이 노드 B의 2001보다 늦게 발급될 수 있다. 단, 서버가 재시작되면 할당받은 구간 중 사용하지 않은 번호가 버려져 ID에 공백(gap)이 생길 수 있다.

## 실무 관점

- **언제/왜**: 샤딩된 데이터베이스, 다중 리전 배포, 이벤트 소싱의 이벤트 ID처럼 여러 주체가 동시에 ID를 발급해야 하는 모든 상황에서 필요하다. 단일 DB만 쓰는 초기 단계 서비스라면 auto-increment로 충분하지만, 샤딩/멀티 마스터 구조로 넘어가는 순간 이 문제를 반드시 해결해야 한다.
- **트레이드오프**: Snowflake류는 정수형이라 저장 공간이 작고 정렬이 쉽지만 노드 ID 관리(코디네이션)가 필요하다. UUID v4와 일반적인 v7 생성은 노드 ID 할당 없이 가능하지만 안전한 난수원·충돌 대응이 필요하며 128비트라 인덱스 크기가 커지고(v4는 랜덤이라 페이지 스플릿도 유발), 가독성이 떨어진다.
- **흔한 실수**: UUID v4를 그대로 기본 키(primary key)로 써서 B-Tree 인덱스에 랜덤 삽입이 발생, 페이지 스플릿과 캐시 미스가 급증해 쓰기 성능이 저하되는 사례가 매우 흔하다. 시간 정렬이 필요한 테이블이라면 UUID v7이나 Snowflake로 전환하는 것이 대안이다.
- **흔한 실수 2**: Snowflake 노드 ID를 정적 설정 파일에 하드코딩하면 스케일 아웃 시 중복 배정 위험이 있다. 컨테이너 환경에서는 전체 발급 범위에서 중복이 없도록 파드 서수의 네임스페이스나 코디네이터 기반 할당·재할당 조건을 설계한다.
- **튜닝 포인트**: 커스텀 에폭을 서비스 시작 시점 근처로 잡아야 41비트 타임스탬프의 유효 기간(약 69년)을 최대한 활용할 수 있다. 시퀀스 비트 수와 노드 ID 비트 수는 예상 노드 수와 노드당 초당 최대 발급량(TPS)에 맞춰 배분한다(예: 노드당 4096 IDs/ms는 산술 상한이 초당 4,096,000건이며 실제 처리량 보장은 아님).

### 큰 정수 ID는 JSON 전달 경로의 정밀도도 확인한다

서버와 DB에서 64비트 정수로 정확하게 보관한 ID도 JSON 숫자로 보내면 JavaScript `Number`를 거치는 클라이언트에서 값이 달라질 수 있다. RFC 8259가 정확한 정수 상호운용 범위로 제시하는 값은 `-(2^53)+1`부터 `2^53-1`까지다. 이 범위를 넘는 Snowflake류 ID는 API에서 처음부터 십진 문자열로 직렬화하고 SDK·브라우저·로그 중계 경로에서도 문자열 계약을 유지한다.

Node.js v26.5.0의 `JSON.parse`에서 숫자 `9007199254740992`와 `9007199254740993`이 같은 값으로 읽히는 것을 확인했다. 숫자로 파싱한 다음 문자열로 바꿔도 잃은 자릿수는 복구되지 않는다. 문자열로 왕복했을 때 두 ID가 구분되는지 검증하며, 서버의 생성 충돌과 전달 중 정밀도 손실을 서로 다른 장애 원인으로 조사한다.

## 심화 Q&A

### Q. Snowflake 방식에서 서버 시계가 역행(NTP 보정 등)하면 어떤 문제가 생기고 어떻게 방어하는가?
타임스탬프가 과거로 돌아가면 이전에 발급한 ID와 동일하거나 더 작은 값이 재발급될 수 있어 유일성과 순서 보장이 깨진다. 실무에서는 마지막으로 사용한 타임스탬프를 기록해 두고, 현재 시각이 그보다 작으면 예외를 던지거나(요청 거부) 차이가 작으면(수 ms 이내) 마지막 타임스탬프까지 대기했다가 발급하는 방식으로 방어한다. NTP는 slew(점진적 보정) 모드로 설정해 급격한 역행 자체를 줄이는 것도 병행한다.

### Q. UUID v4 대신 v7을 쓰면 정말 인덱스 성능이 개선되는가, 그 이유는?
개선 가능성이 있지만 DB의 UUID 비교 방식·인덱스·동시 삽입 부하로 측정해야 한다. v4는 랜덤이라 B-Tree에 삽입될 위치가 매번 무작위로 결정되어 페이지 스플릿과 디스크 랜덤 쓰기가 증가한다. v7은 상위 비트가 타임스탬프라 대체로 최근 값이 모이는 위치에 삽입된다. 시계 차이·과거 ID 재삽입은 이 패턴을 흐릴 수 있고, 순차 삽입의 hot page 경합도 측정한다. PostgreSQL 18은 `uuidv7()`을 기본 제공한다.

### Q. DB 구간 할당(segment) 방식과 Snowflake 중 무엇을 선택해야 하는가?
DB를 기준으로 중복 없는 정수 구간을 관리하면서 매 요청의 DB 접근을 줄이고 싶다면 구간 할당이 적합하다. gap 없는 번호나 전역 생성 순서가 요구되면 구간 할당과 Snowflake 어느 쪽도 단독으로 충분하지 않다. 반면 여러 데이터센터에 분산된 노드가 DB 없이도 독립적으로 ID를 발급해야 하거나, 타임스탬프 자체가 유용한 정보(생성 시각 역산)로 쓰이는 경우에는 Snowflake가 더 적합하다. 구간 할당은 결국 DB(또는 코디네이터)에 대한 의존이 남는다는 점이 Snowflake와의 근본적 차이다.

### Q. 여러 리전에 걸친 멀티 마스터 구조에서 ID 생성 시 리전 정보를 ID에 포함시키는 이유는?
리전 간 노드 ID의 충돌 영역을 나누고, 장애 발생 시 어느 리전에서 생성된 데이터인지 ID만 보고 즉시 판별할 수 있어 트러블슈팅과 데이터 라우팅(리전별 샤드로 되돌리기)이 쉬워진다. Snowflake의 노드 ID 비트를 데이터센터 ID + 워커 ID로 나누는 것이 이런 이유에서다.

### Q. 분산 ID가 노출되는 API 응답에서 UUID나 Snowflake ID를 그대로 쓰면 어떤 보안 문제가 생길 수 있는가?
Snowflake ID는 타임스탬프가 상위 비트에 그대로 드러나므로 생성 순서나 대략적인 생성 시각, 심지어 대략적인 트래픽량(같은 시간대 시퀀스 값)까지 추론 가능하다. 순차적 정수 ID와 마찬가지로 IDOR(Insecure Direct Object Reference) 공격의 스캔 대상이 되기도 쉬우므로, 외부 식별자에 예측하기 어려운 UUID v4 등을 별도로 쓸 수 있다. UUID v7도 생성 시각을 드러낸다. 어떤 식별자를 쓰든 리소스별 접근 권한 검증이 IDOR 방어의 핵심이며 난독화로 이를 대체할 수 없다.

### Q. 시퀀스 비트가 부족해 같은 밀리초 내 발급량이 한도를 초과하면 어떻게 처리하는가?
가장 일반적인 대응은 다음 밀리초까지 짧게 대기(spin-wait)했다가 시퀀스를 0으로 리셋하고 발급하는 것이다. 대기 시간이 감당되지 않을 만큼 트래픽이 몰리면 노드 수를 늘려 노드당 부하를 분산하거나, 시퀀스 비트를 늘리고 노드 ID 비트를 줄이는 트레이드오프를 고려해야 한다.

부분 재검증: 2026-10-04. [RFC 8259 §6 Numbers](https://www.rfc-editor.org/rfc/rfc8259.html#section-6)의 정밀도·상호운용 범위를 확인하고 Node.js v26.5.0의 JSON.parse/stringify로 인접한 큰 정수의 충돌 및 문자열 왕복 보존을 assertion 검증했다. 실제 Snowflake 생성기·서버 직렬화 설정·브라우저·SDK 통합은 실행하지 않았으며, 기존 생성 알고리즘 전체는 재검증하지 않아 `verified`는 유지했다.
