# 시간 복잡도와 공간 복잡도

## 핵심 정의
시간 복잡도(time complexity)는 입력 크기 n에 대해 알고리즘이 수행하는 연산 횟수가 어떻게 증가하는지를 나타내고, 공간 복잡도(space complexity)는 입력 크기에 따른 메모리 사용량의 증가율이다. 입력 저장 공간까지 포함한 전체 공간과 추가 공간(auxiliary space)을 구분하며, 이 노트의 표·코드는 추가 공간을 기준으로 한다. 단위 비용 연산·정수 크기 등의 계산 모델을 정한 뒤 점근적(asymptotic) 분석을 하며, 빅오 표기법(Big-O notation)은 선택한 비용 함수의 점근적 상한을 표현한다. 실무에서는 절대적인 실행 시간보다, 입력이 커질 때 성능이 어떻게 악화되는지를 예측하고 설계 단계에서 병목을 미리 걸러내는 데 쓰인다.

## 동작 원리 / 구조

### 표기법의 의미
- **빅오(O)**: 점근적 상한. 충분히 큰 n에서 어떤 상수 배 이하라는 뜻이며, 느슨한 상한도 가능하다.
- **빅오메가(Ω)**: 점근적 하한. 충분히 큰 n에서 어떤 상수 배 이상이라는 뜻이다.
- **빅세타(Θ)**: 점근적으로 타이트한 경계. 같은 함수에 대해 O와 Ω가 모두 성립한다.

최선·평균·최악은 어떤 입력의 비용을 분석하는지를 정하고, O·Ω·Θ는 그 비용 함수의 경계를 나타낸다. 예를 들어 삽입 정렬은 최선 Θ(n), 최악 Θ(n²)이다. O 자체가 최악, Ω가 최선, Θ가 평균을 뜻하지 않는다.

### 복잡도 증가율 비교 (n이 커질수록)

표의 수치는 log₂를 사용해 대표 함수를 계산한 근삿값이며 실제 실행 시간이나 정확한 연산 수는 아니다.

| 표기 | 이름 | n=10 | n=1,000 | n=1,000,000 | 예시 |
|---|---|---|---|---|---|
| O(1) | 상수 | 1 | 1 | 1 | 배열 인덱스 접근, HashMap 조회(평균) |
| O(log n) | 로그 | 3 | 10 | 20 | 이진 탐색, 균형 트리 탐색 |
| O(n) | 선형 | 10 | 1,000 | 1,000,000 | 배열 순회 |
| O(n log n) | 선형로그 | 33 | 9,966 | 19,931,569 | 효율적 정렬 |
| O(n²) | 이차 | 100 | 1,000,000 | 10¹² | 이중 for문, 버블 정렬 |
| O(2ⁿ) | 지수 | 1,024 | 사실상 계산 불가 | - | 부분집합 완전 탐색 |

### 시간-공간 트레이드오프 예시

아래는 각각 `int[] arr`, `int target`을 받는 별도 메서드의 핵심 루프다. 일치 쌍이 없는 경우의 반환/예외 정책은 생략했다. 합·차는 int 범위를 넘을 수 있어 long으로 계산한다.
```java
// 시간 O(n²), 공간 O(1) - 두 수의 합이 target인 쌍 찾기 (브루트포스)
for (int i = 0; i < arr.length; i++) {
    for (int j = i + 1; j < arr.length; j++) {
        if ((long) arr[i] + arr[j] == target) return new int[]{i, j};
    }
}

// 기대 시간 O(n), 공간 O(n) - 균등한 해시 분포와 상수 비용 비교 가정
Map<Long, Integer> seen = new HashMap<>();
for (int i = 0; i < arr.length; i++) {
    long complement = (long) target - arr[i];
    if (seen.containsKey(complement)) return new int[]{seen.get(complement), i};
    seen.put((long) arr[i], i);
}
```

## 실무 관점
- **자료구조 선택이 곧 복잡도 결정**: `ArrayList.contains()`는 O(n), `HashSet.contains()`는 평균 O(1)이다. 반복문 안에서 리스트 `contains()`를 호출하는 코드는 전체가 O(n²)가 되어, 데이터가 수만 건만 돼도 응답 지연으로 드러난다. 이런 패턴은 코드 리뷰에서 자주 발견되는 실수다.
- **재귀와 공간 복잡도**: 재귀 호출은 콜 스택(call stack)을 소비하므로 스택 오버플로우(StackOverflowError) 위험과 직결된다. 깊이가 n에 비례하는 재귀(예: 리스트 길이만큼 재귀)는 공간 복잡도 O(n)이며, 일반적인 Java 메서드에 꼬리 재귀 최적화(tail call optimization)를 보장하지 않는 JVM에서는 반복문으로 바꾸는 것이 안전하다.
- **N+1 쿼리 문제**: 지연 연관을 n개 순회하면 최초 조회를 포함해 1+n번의 쿼리가 발생할 수 있다. fetch join은 적합한 연관을 한 SQL로 읽지만 전송 행 수와 조인 비용까지 O(1)이 되는 것은 아니다. 크기 B의 배치로 n개 연관을 채우는 단순 모델은 약 1+ceil(n/B)번이며, B가 고정이면 여전히 O(n) 쿼리다. 이는 왕복 횟수·계수를 줄이는 최적화이며 O(log n)으로 바뀌는 것이 아니다.
- **알고리즘 복잡도만으로 실제 성능을 단정하면 안 되는 이유**: 캐시 지역성(cache locality), 상수 계수, 입력 크기가 실제로 작은 경우(n < 100)에는 O(n²) 알고리즘이 O(n log n) 알고리즘보다 실측 속도가 빠를 수 있다. 예를 들어 삽입 정렬은 매우 작은 배열에서 병합 정렬보다 빠르며, 이 때문에 하이브리드 정렬(Timsort 등)이 작은 구간은 삽입 정렬로 처리한다.
- **튜닝 포인트**: 성능 이슈를 복잡도 관점에서 진단할 때는 "입력 크기가 몇 배 늘 때 응답 시간이 몇 배 느는지"를 실측 로그나 APM(Application Performance Monitoring)으로 확인하고, 선형 이상으로 증가한다면 반복문 중첩이나 컬렉션 검색 방식부터 의심하는 것이 효율적이다.

## 심화 Q&A

### Q. O(n)과 O(2n)은 빅오 표기법상 동일하게 취급되는데, 이 둘의 실무 성능 차이가 무의미하다고 볼 수 있는가?
A. 점근적 분석에서는 상수 배수를 무시하므로 이론적으로 동일한 복잡도 클래스지만, 실무에서는 상수 계수(constant factor)가 실제 응답 시간을 좌우하는 경우가 많다. 예를 들어 같은 O(n)이라도 배열을 한 번 순회하는 코드와 같은 배열을 세 번 순회하며 매번 객체를 새로 생성하는 코드는 체감 성능이 크게 다르다. 복잡도 분석은 확장성(scalability)을 예측하는 도구이지, 절대 성능을 보장하는 지표가 아니라는 점을 구분해야 한다.

### Q. 평균 시간 복잡도가 O(1)인 해시맵 조회가 최악의 경우 O(n)이 되는 상황은 언제이고, 어떻게 완화하는가?
A. 충돌이 몰려 체이닝된 리스트를 탐색하면 O(n)까지 저하된다. OpenJDK 25+36은 `TREEIFY_THRESHOLD=8`, `MIN_TREEIFY_CAPACITY=64` 등을 사용하지만 실제 전환 시점은 삽입 경로와 기존 노드 수에 따라 달라진다. 트리 버킷도 같은 해시의 키를 비교로 구분하지 못하면 양쪽을 탐색할 수 있어 모든 키에 최악 O(log n)을 보장하지 않는다. hashCode는 균등하게 분산시키고 equals 계약을 지킨다. 세부 조건은 [[해시 테이블]]을 참고한다.

### Q. 공간 복잡도를 줄이기 위해 시간 복잡도를 희생하는 것이 합리적인 경우는?
A. 메모리가 제한된 환경(임베디드, 대량 동시 요청을 처리하는 서버의 힙 압박 상황)에서는 캐시나 메모이제이션(memoization) 없이 매번 재계산하는 편이 나을 수 있다. 예를 들어 동적 계획법(dynamic programming)에서 전체 DP 테이블을 저장하는 대신 직전 몇 개 상태만 유지하는 "공간 최적화(rolling array)" 기법은 공간을 O(n)에서 O(1)로 줄이되, 이전 결과를 복원해야 하는 경우 시간이 늘어날 수 있다.

### Q. 알고리즘의 점근적 복잡도가 더 낮음에도 실무에서 채택되지 않는 사례를 들 수 있는가?
A. 스트라센 알고리즘(Strassen’s algorithm)은 정사각 행렬 곱셈의 연산 수를 통상적인 Θ(n³)에서 Θ(n^log₂7), 약 Θ(n^2.807)로 낮춘다. 다만 추가 덧셈·메모리·재귀 비용과 수치 오차 특성이 달라 실제 손익분기점은 행렬 크기·라이브러리·하드웨어에 따라 달라진다. 고정된 차원 구간에서 항상 느리다고 단정하지 말고 대상 워크로드로 측정한다.

### Q. 페이지네이션 API에서 `OFFSET` 기반 조회가 뒤쪽 페이지로 갈수록 느려지는 이유를 복잡도로 설명하면?
A. `OFFSET k LIMIT m`은 건너뛸 행도 서버에서 계산하므로, 정렬 인덱스를 따라 k+m개 후보를 읽는 모델에서는 O(k+m) 스캔 비용이 든다. 키셋 페이지네이션은 적합한 복합 인덱스와 고유한 정렬 키가 있을 때 시작 위치 탐색 O(log n)에 결과 m개 스캔 O(m)을 더한 비용으로 설명할 수 있다. 필터 선택도·조인·정렬·테이블 접근이 추가되면 이 단순 모델과 달라지므로 실행 계획으로 확인한다.

### Q. 시간 복잡도가 같은 두 알고리즘 중 하나를 골라야 할 때, 복잡도 외에 추가로 고려해야 할 기준은?
A. 안정성 여부, 최악의 경우 분포(평균은 같아도 분산이 큰 알고리즘은 SLA가 엄격한 서비스에 부적합할 수 있음), 구현 복잡도와 유지보수성, 병렬화 가능 여부, 그리고 실제 운영 환경의 입력 분포(예: 거의 정렬된 데이터가 자주 들어오는지)를 함께 고려해야 한다. 이론적 복잡도가 같아도 실제 워크로드 특성에 따라 선택이 달라질 수 있다.
