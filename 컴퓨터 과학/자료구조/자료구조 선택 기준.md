# 자료구조 선택 기준

## 핵심 정의
자료구조 선택은 저장할 값보다 **자주 수행할 연산과 반드시 지켜야 할 계약**에서 시작한다. 중복 허용, 키 동등성(equality), 순서(ordering), 범위 검색, 동시 수정, 최대 크기를 먼저 정하고 시간·공간 비용을 비교한다. 평균 시간복잡도가 같아도 순회 비용, 메모리 배치, 확장 시 지연은 다를 수 있다.

아래 Java 표준 컬렉션 계약은 Java SE 27 기준이다. 구현 내부의 성장 배율이나 객체 크기를 API 보장으로 간주하지 않는다.

## 동작 원리 / 구조

| 필요한 연산·계약 | 우선 검토할 구조 | 확인할 비용·제약 |
|---|---|---|
| 인덱스 조회와 순차 순회 | 배열, `ArrayList` | 인덱스 조회 O(1); ArrayList 끝 추가 상환 O(1), 중간 이동 O(n); 배열 길이는 고정 |
| 양 끝 삽입·삭제, FIFO/LIFO | `ArrayDeque` | 대부분 상환 O(1), 원소 검색·지정 원소 삭제 O(n), null 금지 |
| 키로 값 찾기, 순서 불필요 | `HashMap` | 적절한 해시 분산에서 평균 O(1), 순회는 크기와 용량에 비례 |
| 삽입 순서 유지 | `LinkedHashMap` | 순서 유지 비용 추가; 접근 순서는 별도 생성 옵션 |
| 정렬된 키와 범위 조회 | `TreeMap` | 기본 키 연산 O(log n), 비교 결과 0이 같은 키 |
| 최솟값/최댓값 반복 추출 | `PriorityQueue` | peek O(1), offer/poll O(log n), 전체 순회는 정렬 순서 아님 |
| 중복 제거 | `HashSet`, `TreeSet` | 각각 equals/hashCode 또는 비교 순서로 동등성 판단 |
| 생산자·소비자 간 유한 대기열 | 용량을 정한 `BlockingQueue` | 포화 시 대기·시간 제한·거부 정책까지 필요 |

`n`은 원소 수이며 키의 해시·비교 비용을 상수로 취급한 복잡도다. 문자열 길이가 크거나 비교자가 DB 접근 같은 작업을 수행하면 그 비용도 포함해야 한다. 상환(amortized) O(1)은 각 요청의 최악 지연이 O(1)이라는 뜻이 아니다.

### 같은 키의 기준부터 확인하기
```java
var a = new java.math.BigDecimal("1.0");
var b = new java.math.BigDecimal("1.00");
var hash = new java.util.HashMap<java.math.BigDecimal, String>();
var tree = new java.util.TreeMap<java.math.BigDecimal, String>();
hash.put(a, "first"); hash.put(b, "second"); // size == 2
tree.put(a, "first"); tree.put(b, "second"); // size == 1
```

`BigDecimal.equals()`는 scale도 비교하고 자연 순서의 `compareTo()`는 수치가 같으면 0을 반환한다. 따라서 HashMap을 TreeMap으로 바꾸면 단순히 출력 순서뿐 아니라 서로 다른 키를 보존하는 방식까지 바뀔 수 있다. 정렬과 `Map`의 일반 동등성 계약을 함께 만족시키려면 비교자가 equals와 일관되어야 한다.

## 실무 관점
- 자료구조 자체의 동시성 지원과 여러 연산의 원자성은 구분한다. `ConcurrentHashMap`도 별도 get 뒤 put 전체를 원자적으로 만들어주지는 않는다. 의도가 맞는 `compute`, `merge`, `putIfAbsent` 등을 선택한다.
- 읽기 대부분·갱신 드문 데이터는 변경 가능한 전역 컬렉션 대신 불변 스냅샷을 만들어 안전하게 교체하는 방법도 검토한다. 스냅샷 복사 비용과 기존 참조의 수명은 남는다.
- 대량 숫자는 `int[]` 같은 기본형 배열과 박싱 컬렉션의 할당량을 비교한다. `ArrayList`의 배열에는 객체 자체가 아니라 참조가 연속으로 저장된다.
- 캐시는 초기 용량만 정한다고 크기가 제한되지 않는다. 최대 항목 수, 만료, 축출(eviction), 중복 로딩을 별도로 설계한다.
- 벤치마크에는 실제 키 분포, hit/miss, 읽기·쓰기 비율, 초기화 이후 정상 상태와 확장 구간을 포함한다. 한 번의 `nanoTime()` 측정으로 구조를 결정하지 않는다.

## 심화 Q&A

### Q. 최소값이 필요하면 TreeMap과 PriorityQueue 중 무엇을 선택하는가?
A. 최소 항목을 계속 꺼내기만 하면 힙(heap) 기반 PriorityQueue가 단순하다. 키로 찾아 갱신하거나 범위·이전/다음 키가 필요하면 TreeMap을 검토한다. PriorityQueue의 `remove(Object)`와 `contains`는 선형 시간이며, 원소의 우선순위 필드를 삽입 후 바꿔도 자동으로 힙 순서가 복구되지 않는다. 갱신 전략을 별도로 정한다.

### Q. 삽입이 많으면 LinkedList가 항상 유리한가?
A. 삽입 위치를 찾는 비용을 포함해야 한다. 이미 확보한 ListIterator 위치에서의 연결 수정과 `add(index, value)`는 다르다. 끝 추가·전체 순회 위주라면 배열의 지역성과 적은 할당 비용이 유리할 수 있고, 큐 용도라면 ArrayDeque를 먼저 검토한다.

### Q. HashMap 평균 O(1)이면 TreeMap의 O(log n)보다 항상 빠른가?
A. 아니다. 해시 계산·충돌·캐시 미스·비교 비용과 요구 연산이 다르다. 예를 들어 특정 키 이하에서 가장 가까운 항목을 찾는 `floorEntry`는 TreeMap이 직접 지원하지만 HashMap은 순서를 유지하지 않아 별도 탐색이 필요하다. 하나의 get 연산만으로 전체 요청 비용을 판단하지 않는다.

### Q. 스레드 안전한 큐면 과부하도 해결되는가?
A. 아니다. 스레드 안전성은 동시 접근 계약이고, 과부하 제어는 생산 속도·소비 속도·용량의 문제다. 무제한 큐가 입력을 계속 받으면 메모리에 대기가 누적된다. 유한 용량과 `offer`의 실패·시간 제한을 호출자가 어떻게 처리하는지까지 정해야 한다.
